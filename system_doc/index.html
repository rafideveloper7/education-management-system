PUBLIC USER

Public Visitor
A Public Visitor Can:
  • Browse the website & view institute information
  • View programs, courses, departments & faculty
  • View public notices, upcoming events & gallery
  • View admission guidelines & criteria
  • Submit online admission application
  • Submit contact messages / general inquiries
  • Register & Login
Critical Security Rule:

Public registration does NOT create an academic account. Academic accounts (Student, Teacher, Parent) are strictly created and controlled by Admin. Public accounts only track submitted admission applications and public inquiries.

COMMUNICATION & APPLICATION SYSTEM

Controlled Workflows
System Rule: This is a major system-wide feature. Users communicate through structured Applications / Requests / Complaints. This should NOT simply be an unrestricted chat system; it is a controlled, auditable communication workflow.
15. Student Applications:

Students submit applications/requests to authorized staff.

Examples:
  • Leave application
  • Fee-related request
  • Academic request
  • Certificate request
  • Document request
  • Class-related issue
  • Teacher-related complaint
  • General complaint
  • Personal request & others
Student Capabilities:

Create app, Select category, Select recipient where permitted, Write details, Attach docs, Submit, View status, View responses, Add info if requested, Track history.

16. Parent Applications:

Parent submits to: Specific teacher where permitted, Class teacher, Relevant dept, Admin, Principal / authorized authority.

Examples:
  • Child leave request
  • Attendance concern
  • Academic concern
  • Fee request & Fee issue
  • Teacher-related complaint
  • Child-related concern
  • Certificate / document request
  • Meeting request
  • General complaint & application
Parent Capabilities:

Submit app, Select child, Select category, Select recipient, Add details, Attach files, Track status, View responses, Continue communication.

17. Teacher Applications:

Teacher submits to: Admin, Principal, Authorized management staff.

Examples:
  • Leave application
  • Schedule request
  • Class-related issue
  • Student-related concern
  • Parent-related concern
  • Resource request
  • Salary / payroll-related request
  • Technical issue
  • General complaint & application
Teacher Capabilities:

Submit, Attach files, Track status, Receive response, Respond when clarification is requested, View application history.

18. Admin / Principal Communication Capabilities: Receives from Teachers, Students, Parents

Admin/Principal can: Review, Assign to another authorized staff member, Request information, Respond, Approve, Reject, Resolve, Close, and Reopen where appropriate. The system maintains a complete history of every application.

19. The Formal Application Workflow:
User Creates App ➔ Selects Category ➔ Selects Recipient ➔ Submitted ➔ Under Review ➔ Need Information ➔ Approved / Resolved ➔ Notification Sent

SECURITY PERMISSION PRINCIPLE & COMPLETE SYSTEM FLOW

Zero-Trust & Blueprint
34. IMPORTANT PERMISSION PRINCIPLE:

Frontend visibility is NOT security.

The backend must deterministically enforce:

  • Who can access
  • Who can create
  • Who can edit
  • Who can approve
  • Who can reject
  • Who can respond
  • Who can close
  • Who can view sensitive information

* A Student must not access another student's data simply by changing an ID in a URL.
* A Parent must only access their linked children.
* A Teacher must only access assigned classes/students.
* An Admin has broader institutional access according to permissions.
